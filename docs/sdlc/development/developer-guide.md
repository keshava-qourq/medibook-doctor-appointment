<!-- sdlc:auto:start overview -->
MediBook is a single repository holding two applications generated by the Quorq AI SDLC platform: a Vite + React 19 single-page frontend (`frontend/`, TypeScript, Tailwind 4, React Router 7, TanStack Query, react-hook-form) and a FastAPI backend (`backend/`, SQLAlchemy 2 ORM, Pydantic 2, bcrypt password hashing and opaque bearer-token sessions). The backend exposes `/health` plus `/api/...` routers for auth (register/login/logout/me), admin user management, medical specializations and disease/symptom catalogue terms, clinic settings, patient self-service profile, admin doctor-specialization linking, term-driven doctor search, and placeholder ownership-guarded appointment/consultation reads. It creates its schema from the models on startup (no migrations) and defaults to a local SQLite file, with `DATABASE_URL` pointing at PostgreSQL 16 for real deployments. The frontend screens currently render seeded sample data; `frontend/src/lib/api.ts` is the seam (base URL, bearer token handling, `apiFetch`) for wiring them to the API.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start setup -->
1. Clone the repository and open it in your editor (a .devcontainer/devcontainer.json is provided if you prefer a container).
2. Copy the example environment file if you want non-default settings: cp .env.example .env
3. Install backend dependencies: cd backend && pip install -r requirements.txt
4. Start the backend (defaults to a local SQLite database at ./app.db): uvicorn app.main:app --reload
5. In a second terminal install frontend dependencies: cd frontend && npm install
6. Start the frontend dev server: npm run dev (its API base URL defaults to http://localhost:8000; override with VITE_API_BASE_URL)
7. Optional: start PostgreSQL and Redis with docker compose up -d, then run the backend against Postgres by setting DATABASE_URL (e.g. DATABASE_URL=postgresql+psycopg://<db-user>:<database-password>@localhost:5432/<db-name>)
8. Optional, before running Playwright e2e tests: create backend/.venv and install requirements into it, because frontend/playwright.config.ts boots the API with backend/.venv/bin/python.
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend: one router module per architecture component under app/routers/, each exporting `router` (or `public_router`/`admin_router`) and an `__all__`.
- Routes are prefixed /api (auth under /api/auth, admin surfaces under /api/admin); /health is unprefixed.
- Role enforcement is via dependencies: `current_user` for authenticated reads, `require_role("admin"\|"patient")` for role-scoped routers; identity always comes from the bearer token, never the request body.
- Validation errors are normalised to 422 `{"detail": [{"field", "msg"}]}`; conflicts return a `code` (e.g. `email_in_use`, `duplicate_name`, `in_use`); 403/404 that must not leak information raise `EmptyBodyHTTPError` and return no body.
- Pydantic schemas live in app/schemas.py as request/response pairs; `AliasChoices` accepts both contract and legacy field names. Passwords are never present in read schemas.
- SQLAlchemy 2 declarative models with `Mapped[...]`/`mapped_column`, string UUID primary keys, a `CIText` TypeDecorator (CITEXT on Postgres, String elsewhere), and soft deletion/deactivation (`is_active`, `is_deleted`) instead of hard deletes for referenced rows.
- Schema is created at startup from the models (no Alembic yet); `DATABASE_URL` falls back to SQLite so a fresh clone runs with no database server.
- Frontend: path alias `@/` maps to `src/`; screens in src/screens/, shared primitives in src/lib/; routing and role guards (`RequireRole`) are declared in App.tsx.
- Styling uses Tailwind plus CSS custom properties for brand tokens (`var(--brand-*)`).
- Vitest component tests sit beside the component as *.test.tsx under src/; Playwright specs live in e2e/ and are excluded from the Vitest include pattern.
- All HTTP access from the SPA goes through `apiRequest`/`apiFetch` in src/lib/api.ts, which attaches the stored session bearer token and throws `ApiError` for non-2xx responses.

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| `pytest` fails with `ModuleNotFoundError: No module named 'app'`. | Run pytest from the backend/ directory so pytest.ini's `pythonpath = .` applies. |
| Browser requests from the SPA are blocked by CORS. | The backend allows localhost/127.0.0.1 on ports 5173 and 4173 by default; for any other origin set ALLOWED_ORIGINS (comma separated) before starting uvicorn. |
| The app starts but cannot reach the database, or you want PostgreSQL instead of SQLite. | Start the compose services (docker compose up -d) and set DATABASE_URL to your Postgres URL using placeholders for credentials, e.g. postgresql+psycopg://<db-user>:<database-password>@localhost:5432/<db-name>; leave it unset to use the default sqlite:///./app.db. |
| Startup fails immediately with a session idle configuration error. | SESSION_IDLE_MINUTES is validated at startup by validate_session_idle_minutes(); correct the value to a valid number and restart. |
| Playwright's webServer step fails because backend/.venv/bin/python does not exist. | Create the virtualenv the config expects: cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt, then rerun npm run test:e2e. |
| `npm run build` succeeds but deployment-style typechecking fails. | `vite build` does not typecheck; run npm run typecheck (tsc --noEmit) and fix the reported errors. |
| Frontend calls go to http://localhost:8000 in a deployed build. | VITE_API_BASE_URL is inlined at build time; set it before running npm run build (the deploy workflow does this). |
| E2E specs that count accounts behave inconsistently. | They assume a clean database; the Playwright config removes backend/e2e.db and starts a fresh backend, so do not point the run at an accumulated ./app.db. |
<!-- sdlc:auto:end troubleshooting -->
